\chapter{Interactive Notebook Infrastructure and Kernel Architecture}
\label{chap:interactive_kernels}

Interactive computational notebooks---pioneered by Mathematica and popularized across academia by Project Jupyter~\cite{kluyver2016jupyter,perez2007ipython}---have revolutionized computing education. In formal languages and automata theory, notebooks replace static pseudocode with executable mathematical models. Students can define non-deterministic finite automata ($\text{NFA}$), compute power-set determinizations ($\text{DFA}$), minimize states via partition refinement, and immediately inspect rendered transition graphs and syntax trees within the browser.

However, hosting rigorous symbolic computation inside an interactive notebook imposes non-trivial architectural challenges. A programming language's runtime is no longer invoked as an ephemeral, single-shot batch process. Instead, an interactive \textbf{kernel} process persists indefinitely across multiple HTTP and ZeroMQ requests~\cite{hintjens2013zeromq}, executing disjoint user-submitted cells in arbitrary order while maintaining live heap memory, open file descriptors, and dynamic symbol tables.

This chapter investigates the interactive notebook infrastructure across our tri-language corpus:
\begin{enumerate}
  \item \textbf{Python 3.13} hosted via the reference \texttt{ipykernel} engine;
  \item \textbf{OCaml 5.4} hosted via the native \texttt{ocaml-jupyter} kernel~\cite{akabe2024ocaml}; and
  \item \textbf{F\# 9.0 (.NET 9)} hosted via Microsoft's polyglot \texttt{dotnet-interactive} engine~\cite{dotnetinteractive2024}.
\end{enumerate}
We analyze how the underlying message-passing protocols, toplevel compilation models, variable shadowing rules, generative type semantics, and inline Graphviz rendering pipelines impact state isolation, execution determinism, and pedagogical ergonomics.

\section{Jupyter Wire Protocols and Kernel Architecture}
\label{sec:kernels_protocol}
% ------------------------------------------------------------------------------

The Jupyter architecture unifies heterogeneous execution backends through a language-agnostic wire protocol layered over \textbf{ZeroMQ} asynchronous message sockets and \textbf{JSON} payloads~\cite{hintjens2013zeromq,kluyver2016jupyter}. A Jupyter server and an active language kernel communicate over five dedicated bidirectional and pub/sub channels (\Cref{fig:jupyter_zeromq_architecture}):
\begin{description}
  \item[\textbf{Shell Channel (ROUTER/DEALER):}] Handles interactive code execution requests (\texttt{execute\_request}), code completion requests (\texttt{complete\_request}), and object inspection requests (\texttt{inspect\_request}), returning structured execution metadata and execution counters.
  \item[\textbf{IOPub Channel (PUB/SUB):}] A high-throughput broadcast channel streaming standard output (\texttt{stdout}), standard error (\texttt{stderr}), rich multi-MIME visual representations (\texttt{display\_data}, \texttt{execute\_result}), and execution state indicators (\texttt{status: busy/idle}).
  \item[\textbf{Control Channel (ROUTER/DEALER):}] A prioritized out-of-band channel reserved for administrative interrupts (\texttt{interrupt\_request}), execution termination, and kernel shutdown signals, bypassing clogged queues on the Shell socket.
  \item[\textbf{Stdin Channel (ROUTER/DEALER):}] Enables the kernel to request interactive text input from the client frontend via pseudo-synchronous message pairing (\texttt{input\_request}/\texttt{input\_reply}).
  \item[\textbf{Heartbeat Channel (REQ/REP):}] Emits periodic liveness probes to detect kernel deadlocks, segmentation faults, or unhandled process crashes.
\end{description}

While all three language kernels conform to this external wire specification, their internal execution engines operate under profoundly divergent paradigms:

\subsection{1. Python 3.13: In-Process Interpreted Execution (\texttt{ipykernel})}
The standard Python kernel (\texttt{ipykernel}) executes within a persistent CPython interpreter process managed by an asynchronous \texttt{asyncio}/\texttt{tornado} event loop. User-submitted cells are parsed into CPython bytecode via the built-in \texttt{compile()} function and executed directly in the global module namespace \texttt{\_\_main\_\_.\_\_dict\_\_}. 

Because execution occurs within an interpreted dictionary space, reflection and runtime modification are frictionless: functions, classes, and global constants can be rebound dynamically, and external libraries are imported into the active namespace via standard \texttt{import} statements or \texttt{\%pip} magics. However, as demonstrated in \Cref{chap:performance}, this in-process dynamic design provides no memory or isolation boundaries: objects allocated during cell execution remain anchored in memory unless explicitly garbage collected or overwritten, and uncaught exceptions leave interpreter state partially mutated.

\subsection{2. OCaml 5.4: Compiler-as-a-Library Toploop (\texttt{ocaml-jupyter})}
The OCaml kernel, developed by Akinori Abe~\cite{akabe2024ocaml}, integrates directly with OCaml's internal compiler libraries (\texttt{compiler-libs.toplevel}) and the \texttt{Lwt} cooperative concurrency framework. The kernel process runs an event-driven loop that binds ZeroMQ file descriptors to Lwt asynchronous event listeners.

When a code cell is submitted via the Shell socket, \texttt{ocaml-jupyter} routes the text directly through the OCaml compiler frontend:
\begin{enumerate}
  \item The text is lexed and parsed into an abstract syntax tree representation of toplevel phrases (\texttt{Parsetree.toplevel\_phrase});
  \item The phrase undergoes complete static type checking and Hindley--Milner type inference against the toplevel environment (\texttt{Env.t});
  \item The type-checked phrase is translated into Lambda intermediate code and compiled into native bytecode or machine instructions via \texttt{Toploop.execute\_phrase};
  \item The resulting value is printed using registered value formatters (\texttt{Toploop.install\_printer}) and piped to IOPub.
\end{enumerate}

Unlike Python, where syntax and runtime execution are coupled, \texttt{ocaml-jupyter} enforces full ahead-of-execution static type checking for every cell. If a cell contains a type mismatch or an unbound variable, execution is aborted at phase~2 before any side effects or heap mutations occur.

\subsection{3. F\# 9.0 (.NET 9): Roslyn-Hosted Submission Assembly Pipeline (\texttt{dotnet-interactive})}
Microsoft's \texttt{dotnet-interactive} engine is an enterprise-grade, multi-language polyglot notebook kernel designed to orchestrate C\#, F\#, PowerShell, and SQL within a single session~\cite{dotnetinteractive2024}. The F\# kernel is implemented on top of the \textbf{F\# Compiler Service} (\texttt{FSharp.\allowbreak Compiler.\allowbreak Service}, or FCS) hosted within the .NET 9 CoreCLR runtime.

Rather than interpreting code in a script toploop, \texttt{dotnet-interactive} treats each cell evaluation as an incremental compilation unit termed a \textbf{Submission}:
\begin{enumerate}
  \item The text of Cell~$k$ is analyzed, type-checked, and compiled by the in-memory F\# Compiler Service as a synthetic submission class (e.g., \texttt{Submission\#k});
  \item The compiler emits an in-memory Common Intermediate Language (CIL) assembly fragment referencing all prior submission assemblies (\texttt{Submission\#0} through \texttt{Submission\#(k-1)});
  \item The .NET CoreCLR loader loads the generated assembly into the running process;
  \item RyuJIT compiles the newly loaded CIL into native machine instructions on demand;
  \item The static entrypoint of the submission is invoked, evaluating expressions and returning results to the kernel host.
\end{enumerate}

This architecture guarantees true native JIT performance for numerical and scanner loops, but explains the significant memory overhead and initialization latency observed in \Cref{chap:performance}: the kernel must embed an entire optimizing production compiler, type checker, and assembly emitter in memory.

\section{State Isolation, Variable Shadowing, and Type Generativity Hazards}
\label{sec:kernels_state_hazards}
% ------------------------------------------------------------------------------

The defining characteristic of an interactive notebook is that code cells are rarely executed strictly from top to bottom. During exploratory learning and debugging, students repeatedly re-execute earlier cells, introduce revised type definitions, and modify helper functions. This non-linear execution lifecycle exposes critical divergence in how the three languages handle state mutation and type redefinition.

\subsection{1. Dynamic Rebinding vs. Leaked Closures in Python}
In Python, re-evaluating a cell simply rebinds identifiers in the module's global symbol dictionary. For example, consider defining an AST class and an evaluator function across two cells:

\begin{lstlisting}[language=Python,caption={Python dynamic class re-instantiation anomaly.}]
# Cell 1:
class Node:
    def __init__(self, val, left=None, right=None):
        self.val, self.left, self.right = val, left, right

root = Node("+", Node(3), Node(4))

# User modifies Cell 1 and re-runs:
class Node:
    def __init__(self, val, left=None, right=None, tag=None):
        self.val, self.left, self.right, self.tag = val, left, right, tag
\end{lstlisting}

Upon re-evaluating Cell~1, the identifier \texttt{Node} points to the new class object. However, any existing AST instance constructed during earlier executions (or stored in data structures across other cells) remains bound to the \textit{original} class object in memory. While Python's dynamic duck typing permits operations that inspect structural attributes (such as \texttt{.val}), nominal identity tests (\texttt{isinstance(root, Node)}) silently evaluate to \texttt{False}, creating subtle, non-deterministic bugs that confuse students.

\subsection{2. The Generative Type Hazard in OCaml's Toploop}
In statically typed functional languages with algebraic data types, type re-evaluation poses a more severe theoretical dilemma: \textbf{type generativity}.

In OCaml, every evaluated type declaration creates a \textit{new, distinct nominal type stamp} in the toplevel environment. Suppose an AST type is declared in Cell~1 and an evaluator is declared in Cell~2:

\begin{lstlisting}[language=Caml,caption={The OCaml toplevel generative nominal type hazard.}]
(* Cell 1: Initial definition *)
type expr = Num of int | Add of expr * expr
let e1 = Add (Num 3, Num 4)

(* Cell 2: Evaluator function *)
let rec eval = function
  | Num n -> n
  | Add (a, b) -> eval a + eval b

(* User re-executes Cell 1 (e.g., adding a Mul constructor): *)
type expr = Num of int | Add of expr * expr | Mul of expr * expr
\end{lstlisting}

If the student now calls \texttt{eval e1} without re-executing Cell~2, the OCaml type checker immediately halts with a bewildering error:
\begin{lstlisting}[language=Caml]
Error: This expression has type expr/1 but an expression was expected of type expr/2
\end{lstlisting}
The toplevel environment contains two structurally identical but nominally distinct types: the old type \texttt{expr/1} associated with the compiled \texttt{eval} function, and the new type \texttt{expr/2} bound to newly constructed expressions. Because Hindley--Milner type inference enforces absolute soundness, values of \texttt{expr/1} cannot unify with \texttt{expr/2}.

\begin{observation}[\textbf{The Toplevel Generative Library Anti-Pattern}]
If shared domain types (such as \texttt{nfa}, \texttt{dfa}, or \texttt{ast}) are defined directly inside notebook cells, re-executing earlier cells in an OCaml notebook will repeatedly invalidate all subsequent functions and values in the heap.
\end{observation}

To resolve this issue, the OCaml curriculum repository establishes an architectural abstraction in \texttt{ocaml/lib/nb.ml}. Shared types are extracted into modular library files and loaded via a guarded idempotent loader:

\begin{lstlisting}[language=Caml,caption={Idempotent library loading pattern in \texttt{ocaml/lib/nb.ml}.}]
let loaded_libs : (string, unit) Hashtbl.t = Hashtbl.create 8

let load_lib (file : string) : unit =
  if not (Hashtbl.mem loaded_libs file) then begin
    let path = Filename.concat lib_dir file in
    if not (Toploop.use_silently Format.std_formatter (Toploop.File path)) then
      failwith ("could not load " ^ file);
    Hashtbl.add loaded_libs file ()
  end
\end{lstlisting}

By registering every loaded module in \texttt{loaded\_libs} and evaluating it via \texttt{Toploop.\allowbreak use\_silently}, the kernel ensures that core type definitions are evaluated \textbf{strictly once per kernel lifecycle}. Re-running a cell containing \texttt{load\_lib "regex.ml"} is a benign no-op, preserving type identity across all existing heap structures.

\subsection{3. F\# Incremental Submission Shadowing}
In \texttt{dotnet-interactive}, F\# resolves the re-execution challenge through Roslyn-style incremental submissions. When a cell is re-executed, the F\# Compiler Service emits a new assembly (\texttt{Submission\#k}) that lexically \textbf{shadows} previous definitions with the same name. 

Unlike OCaml's toplevel, where re-executing a cell can leave existing values typed against stale nominal stamps in the same scope, F\# treats each cell submission as an explicit outer scope wrapping earlier submissions. Furthermore, shared algorithmic functions and automata types are isolated into external \texttt{.fsx} script files loaded via \texttt{\#load "AutomataTypes.fsx"}. Re-loading a script creates a clean namespace boundary, mitigating subtle shadowing collisions while guaranteeing strict type safety.

A 20-state finite automaton or a deeply nested LR parse tree is visually incomprehensible when formatted as raw records or tuples. Consequently, inline visual rendering via Graphviz DOT diagrams and Scalable Vector Graphics (SVG) forms an indispensable component of the interactive curriculum.

\subsection{1. Python: Dynamic Object Protocols}
Python relies on the third-party \texttt{graphviz} library and Jupyter's rich display protocol. When an object provides a \texttt{\_repr\_\allowbreak svg\_()} method (or when wrapped in \texttt{IPython.\allowbreak display.SVG}), the kernel serializes the object to an SVG string and automatically transmits an \texttt{IOPUB\_DISPLAY\_DATA} packet tagged with MIME type \texttt{image/\allowbreak svg+xml}. 

While syntactically transparent, Python's pipeline is susceptible to duplicate state name collisions unless unique node IDs are manually tracked through hash maps or counter objects.

\subsection{2. OCaml: Standalone Graph DSL and Subprocess Orchestration}
OCaml possesses no direct equivalent of Python's sprawling visualization ecosystem. Instead, the curriculum authors constructed a lightweight, self-contained Graphviz abstraction in \texttt{ocaml/lib/graphviz.ml} and \texttt{ocaml/lib/notebook.ml}:

\begin{lstlisting}[language=Caml,caption={OCaml Graphviz execution and IOPub synchronization in \texttt{ocaml/lib/notebook.ml}.}]
let display mime s =
  ignore (Jupyter_notebook.display mime s);
  Unix.sleepf 0.05

let dot_to_svg ?(engine = "dot") (dot : string) : string =
  let input = Filename.temp_file "graph" ".dot" in
  let output = Filename.temp_file "graph" ".svg" in
  write_file input dot;
  let cmd = Printf.sprintf "dot -K%s -Tsvg %s -o %s" 
              (Filename.quote engine) (Filename.quote input) (Filename.quote output) in
  if Sys.command cmd <> 0 then failwith "dot failed";
  let svg = read_file output in
  Sys.remove input; Sys.remove output;
  svg

let display_svg s = display "image/svg+xml" s
\end{lstlisting}

Two critical technical insights emerge from this implementation:
\begin{enumerate}
  \item \textbf{Filesystem-Mediated Subprocess Execution:} To avoid complex cross-platform shell pipe management in pure OCaml, \texttt{dot\_to\_svg} writes the generated DOT specification to a secure temporary file (\texttt{Filename.temp\_file}), invokes the system \texttt{dot} executable via \texttt{Sys.command}, reads the resulting SVG file back into memory, and unlinks both temporary files.
  \item \textbf{The ZeroMQ Race Condition Workaround (\texttt{Unix.sleepf 0.05}):} In the Jupyter messaging protocol, standard text output (\texttt{stdout}) and rich multimedia displays (\texttt{iopub}) travel through asynchronous message queues. In headless execution tools (such as \texttt{nbclient} or automated graders), a cell may report completion (\texttt{status: idle} on the Shell socket) before the IOPub display buffer has been fully dispatched by the kernel thread. Without an explicit $50\text{ ms}$ pause (\texttt{Unix.sleepf 0.05}), automated conversion pipelines (\texttt{jupyter nbconvert}) frequently drop generated SVG diagrams.
\end{enumerate}

Furthermore, the OCaml notebook environment includes native support for Vega-Lite statistical graphics by directly manufacturing low-level \texttt{IOPUB\_DISPLAY\_DATA} JSON payloads via \texttt{Jupyter\_notebook\_\_Unsafe.send\_iopub}, allowing declarative visualization without installing heavy external graphics libraries.

\subsection{3. F\#: Preorder Addressing and Zero-Tempfile Asynchronous Streaming}
F\#'s visualization pipeline (\texttt{f\#/Support/Visualization.fsx}) demonstrates an architecturally superior approach to process orchestration and tree disambiguation:

\begin{lstlisting}[language=FSharp,caption={Preorder structural addressing and stream-piped rendering in F\#.}]
type Tree = Leaf of string | Node of string * Tree list

/// Preorder addresses distinguish repeated labels without relying on object identity.
let assignNumbers tree =
    let rec visit address next tree numbers =
        let numbers = Map.add address next numbers
        match tree with
        | Leaf _ -> next + 1, numbers
        | Node (_, children) ->
            children
            |> List.indexed
            |> List.fold (fun (counter, known) (index, child) ->
                visit (address @ [index]) counter child known) (next + 1, numbers)
    visit [] 0 tree Map.empty |> snd

let renderDot (dot: string) =
    let settings = ProcessStartInfo("dot")
    settings.ArgumentList.Add "-Tsvg"
    settings.UseShellExecute <- false
    settings.RedirectStandardInput <- true
    settings.RedirectStandardOutput <- true
    use graphviz = new Process(StartInfo = settings)
    graphviz.Start() |> ignore
    let output = graphviz.StandardOutput.ReadToEndAsync()
    graphviz.StandardInput.Write dot
    graphviz.StandardInput.Close()
    graphviz.WaitForExit()
    output.GetAwaiter().GetResult()
\end{lstlisting}

This design exhibits two significant advantages:
\begin{enumerate}
  \item \textbf{Preorder Tree Path Addressing:} In compiler parse trees, duplicate terminal and non-terminal symbols appear frequently (e.g., multiple \texttt{expr} or \texttt{"+"} nodes). In Python, disambiguating such nodes requires pointer identity or mutable counters. F\#'s functional \texttt{assignNumbers} assigns unique identifiers based on structural tree coordinates ($\text{preorder address}\in \mathbb{N}^*$), guaranteeing deterministic node labels regardless of label duplication or tree balance.
  \item \textbf{Zero-Filesystem Subprocess Streaming:} Unlike OCaml's reliance on temporary disk files, F\# utilizes .NET's asynchronous process streams (\texttt{RedirectStandardInput} and \texttt{RedirectStandardOutput}). The DOT graph is written directly to the child process's standard input stream, and the generated SVG is consumed asynchronously from standard output. This eliminates all filesystem I/O, temporary file collisions, and race conditions.
\end{enumerate}

\section{Kernel Ergonomics, Diagnostics, and Automated Verification}
\label{sec:kernels_ergonomics}
% ------------------------------------------------------------------------------

Educational usability hinges on the precision of diagnostic feedback when students construct ill-formed grammars or faulty automata.

\subsection{1. Diagnostic Precision and Error Reporting}
When a student introduces a syntactic or semantic error in a notebook cell, the three kernels deliver sharply contrasting diagnostic experiences:
\begin{itemize}
  \item \textbf{Python (\texttt{ipykernel}):} Errors are reported as dynamic runtime exceptions accompanied by lengthy traceback stacks. While syntax errors display line and column pointers, semantic bugs (such as passing a string instead of a set to an NFA transition function) fail deeply inside library internals with generic \texttt{KeyError} or \texttt{AttributeError} messages, obscuring the conceptual root cause.
  \item \textbf{OCaml (\texttt{ocaml-jupyter}):} Compiler errors are emitted before execution begins. The kernel highlights the exact character range of the offending expression with visual underlines and provides rigorous Hindley--Milner unification diagnostics. For instance, attempting to supply an integer state to a transition expecting a state set produces an immediate static error:
  \begin{lstlisting}[language=Caml]
Error: This expression has type int but an expression was expected of type FSet.t
  \end{lstlisting}
  The primary diagnostic drawback remains the aforementioned generative nominal type mismatch (\texttt{type expr/1 vs expr/2}) when cells are re-executed out of order.
  \item \textbf{F\# (\texttt{dotnet-interactive}):} The F\# Compiler Service surfaces structured compiler diagnostics complete with formal error codes (e.g., \texttt{FS0001: Type mismatch}, \texttt{FS0025: Incomplete pattern matches on this expression}). Crucially, pattern exhaustiveness checking provides students with explicit counterexamples when an AST interpreter omits an operator case, transforming compiler diagnostics into an interactive pedagogical tutor.
\end{itemize}

\subsection{2. Automated Curriculum Verification and Continuous Integration}
A critical requirement for large-scale university deployments is the ability to validate entire notebook suites automatically in continuous integration (CI) pipelines:
\begin{itemize}
  \item In Python, automated testing is performed using \texttt{pytest} paired with \texttt{nbclient}, executing notebooks top-to-bottom and checking for unhandled exceptions.
  \item In OCaml, the curriculum includes a standalone verification tool (\texttt{tools/\allowbreak check.py}) that instantiates headless \texttt{ocaml-jupyter} kernels, executes all 50 notebooks sequentially, and validates that every code cell passes static type-checking and execution without failure.
  \item In F\#, the verification infrastructure is multi-tiered: \texttt{python FSharp/tools/notebooks.py} provides a \texttt{check} command for cell metadata and clean formatting, an \texttt{fsi} mode that compiles and runs deterministic notebooks through the headless F\# Interactive compiler, and a full \texttt{jupyter} mode that executes every cell inside the actual .NET interactive kernel, capturing and verifying rich HTML/SVG diagrams into an isolated artifact directory.
\end{itemize}

In summary, while Python offers the lowest barrier to initial entry, its dynamic state mutability introduces insidious state-leakage hazards during interactive cell re-execution. OCaml delivers uncompromising static verification and minimal memory overhead, though requiring careful architectural encapsulation to neutralize generative type hazards. F\# provides an exceptionally robust, modern interactive platform, combining structural tree disambiguation, zero-tempfile process streaming, and exhaustive pattern-match diagnostics at the expense of higher runtime memory residency.

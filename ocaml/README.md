OCaml Versions of the Notebooks of Chapters 1 – 13
=================================================

This directory contains OCaml translations of the Python notebooks in `../Python/Chapter-01` up to
`../Python/Chapter-13`, together with `AST2Dot.ipynb`, which the notebooks of chapter 11 load.  (Chapter 12
contains no notebooks.)  The notebooks have the same names and the same structure as the Python
notebooks: the markdown cells are taken over and only changed where they talk about Python, and every code
cell is translated into the corresponding OCaml code.  `00-Introduction-to-Python-Type-Annotations.ipynb`
has become `00-Introduction-to-OCaml-Types.ipynb`, and the new notebook `Chapter-04-05/Types.ipynb`
contains the types that are shared by the notebooks of chapters 4 and 5.

Like the Python notebooks, the notebooks are stored without outputs.

Setup
-----

The notebooks use the Jupyter kernel [ocaml-jupyter](https://github.com/akabe/ocaml-jupyter) and OCaml 5.

```
brew install opam pcre2 graphviz          # graphviz provides the program dot
opam init
opam install jupyter yojson pcre2 uucp menhir
pip install jupyterlab
ocaml-jupyter-opam-genspec
jupyter kernelspec install --user --name ocaml-jupyter "$(opam var share)/jupyter"
```

Start `jupyter lab` in this directory and select the kernel *OCaml*.

Checking the Notebooks
----------------------

```
python3 tools/check.py
```

executes all notebooks without a browser and reports every cell that fails.  As the OCaml kernel type checks
every cell before it is executed, this is also the type check of the notebooks, i.e. it replaces
`basedpyright`.  Some cells contain type errors on purpose; they are tagged with `raises-exception`.

The Directory `lib`
-------------------

Every notebook starts with `#use "../lib/nb.ml";;`, which loads

| File          | Contents                                                                                  | Replaces                         |
|---------------|-------------------------------------------------------------------------------------------|----------------------------------|
| `notebook.ml` | `display_html`, `display_svg`, `display_text`, `display_vegalite`, `load_css`, `dot_to_svg`, `run_notebook`, `repr`, `ljust`, `rjust`, `cat`, `shell` | `IPython.display`, `%run`, `repr`, `f'{s:n}'`, `!cmd` |
| `fset.ml`     | the polymorphic immutable modules `FSet` (sets) and `Dict` (dictionaries)                 | `set`, `frozenset`, `dict`       |

Further files are loaded with `load_lib`:

| File           | Contents                                                       | Replaces              |
|----------------|----------------------------------------------------------------|-----------------------|
| `regex.ml`     | the module `Re`: `findall`, `finditer`, `search`, `sub`, ... on top of PCRE2 | `re`     |
| `graphviz.ml`  | the module `Graphviz`: building and rendering directed graphs  | `graphviz`            |
| `html5.ml`     | the table `html5` of named HTML entities, generated by `tools/gen_html5_entities.py` | `html.entities.html5` |
| `parser_generator.ml` | `generate_parser` (runs `ocamllex` and `menhir --lalr`, loads the generated modules), `generate_parser_with ~options` (other Menhir options, e.g. `--strict`, `--canonical`, `--GLR`), `generate_lexer` and `generate_grammar` (the two halves separately), `Grammar_error`, the module `Parse_tree` (Lark-style parse trees, `pretty`, `parse_string`, `Unexpected_input`, `get_context`) | `lark`, `ply` |

Apart from these, the notebooks only use the opam packages `uucp` (instead of `unicodedata`), `pcre2`,
`yojson`, `menhirGLR` (installed with `menhir`, only for the GLR parsers of chapter 11), and the tools `ocamllex` and
`menhir`.  The compilers of chapter 13 need `jasmin` and `java`, like the Python version.  The plot of `03-Exam-Evaluation.ipynb` is described in [Vega-Lite](https://vega.github.io/vega-lite/),
which *JupyterLab* displays without any further package (instead of `matplotlib`).

Translation Notes
-----------------

* **Types.**  The regular expressions are a variant type (`Empty | Epsilon | Char of char | Star of regexp |
  Product of ... | Sum of ...`) instead of nested tuples with the special values `0` and `'𝜀'`.  Finite state
  machines are records of the types `'q nfa` and `'q dfa`, where `'q` is the type of the states.  Token kinds,
  scanner states, and stack markers are variant types instead of strings.  Hence the compiler checks that every
  `match` is complete, and none of the `# type: ignore` comments of the Python notebooks is needed.
* **Sets.**  `FSet.t` represents a set as a sorted list without duplicates.  Since every set has exactly one
  representation, sets of sets and pairs of sets can be compared with `=` and `compare`, as in Python.  Set
  comprehensions are written with `let*` and `return`, e.g. `let open FSet in let* x = a in let* y = b in return (x, y)`.
* **Definitions across cells.**  Functions that call functions defined in later cells use *forward references*
  (`let f_ref = ref not_yet_defined` ... `f_ref := f`), so that every function keeps its own cell.  In
  `03-Regexp-2-NFA.ipynb` these references play the role of the stubs of the class `RegExp2NFA`.
* **`%run`.**  `run_notebook "X.ipynb"` executes the code cells of a notebook, but every notebook is loaded at
  most once, since loading it again would create new types that are incompatible with the old ones.
* **Outputs.**  Values are shown in OCaml syntax, e.g. `Star (Char 'a')` instead of `('a', '*')`, strings in
  double quotes, and booleans as `true` and `false`.  Apart from that, the outputs of chapters 1 – 3 are the
  same as those of the Python notebooks.  In chapters 4 and 5, the sets of OCaml are sorted while the sets of
  Python are ordered by hash values.  Therefore, the names `S0`, `S1`, ... of the states of a *Dfa* and the
  regular expressions computed by `dfa_2_regexp` (and hence the sizes in `11-Intersection.ipynb` and
  `12-Complement.ipynb`) may differ from the Python version; all results are checked to be correct.
  `Test-Simplify.ipynb` uses OCaml's random number generator, so its random expressions differ, too.
* **Input.**  The OCaml kernel can not read from the keyboard.  The notebooks that need input call
  `simulate_input [...]` with the lines the user is assumed to type; `input` then returns them one by one.
* **Lark → ocamllex and Menhir (chapters 7 – 10).**  A Lark grammar is split into a scanner specification for
  `ocamllex` and a grammar for `Menhir`, which are given as strings in the notebooks and written to the directory
  `_build` (ignored by git) by `generate_parser`.  `menhir --lalr` corresponds to `parser='lalr'`.  The semantic
  actions build Lark-style parse trees: an alias like `-> add` becomes `Tree ("add", ...)`, and a rule marked with
  `?` returns its child.  Hence the functions that convert parse trees (`ast_to_tuples`, `Transformer`, `pretty`,
  `lex`) keep their roles; they produce typed abstract syntax trees instead of nested tuples.  The LALR states that
  the Python notebook computes with `formal_methods_viz.py` are taken from Menhir's automaton dump.
* **Numbers in interpreted languages.**  `02-Differentiator.ipynb` and the interpreters of chapter 8 reproduce
  Python's arithmetic (`/` returns a float, `%` takes the sign of the divisor, `1 == 1.0`) and print floats like
  Python (`float_repr`).  OCaml's integers have 63 bits, while Python's are unbounded.
* **`eval`.**  The tests of chapter 6 compare with Python's `eval`; the OCaml version evaluates the expression with
  the OCaml toplevel (`Toploop`).
* **Classes with methods added later** (`EarleyItem`, `ShiftReduceParser`, `Grammar`, ...) become modules that are
  extended cell by cell with `module M = struct include M let f ... end`.
* **Large outputs.**  The kernel forwards printed text line by line and can lag behind when a cell prints thousands of
  lines.  The table generators of chapter 10 therefore collect their output in a buffer and show it with `display_text`.
* **Conflicts (chapter 11).**  `Menhir` always prints its warnings about conflicts, so the logger settings and
  `debug=True` of Lark are not needed.  `generate_parser_with ~options:"--lalr --strict"` corresponds to
  `strict=True`: the warnings become errors and the exception `Grammar_error` is raised.  Unlike Lark, Menhir does
  not reject reduce/reduce conflicts by default, therefore `03-Look-Ahead` and `05-Mysterious-Conflicts` use
  `--strict`.  The explanations of the conflicts (`_build/<name>_parser.conflicts`) and the states of the automaton
  (`_build/<name>_parser.automaton.resolved`) replace the warnings and the function `dump_states` of the Python
  version.  Menhir shows only the kernel items of a state, and its numbering of the states differs from Lark's.
  Lark's Earley parser is replaced by Menhir's GLR parser (`--GLR`).  `05-Mysterious-Conflicts` additionally shows
  that Menhir's canonical LR(1) construction (`--canonical`) has no conflict for this grammar.
* **Compilers (chapter 13).**  `Compiler.ipynb` (Lark in Python) uses a stratified Menhir grammar, while
  `Compiler-For.ipynb` (`ply` in Python) uses Menhir's precedence declarations `%nonassoc`, `%left`, `%right`, and
  `%prec`.  In `Compiler-For.ipynb` the scanner is tested before the grammar exists, so the tokens are defined by the
  module `Tokens` and the grammar uses them via `--external-tokens Tokens`.  The abstract syntax trees are typed
  (`expr`, `bool_expr`, `stmnt`, `fct`); they are printed as the nested tuples of the Python version.  The generated
  files `Primes.jas` and `PrimesFor.jas` are identical to those of the Python version.  `%cd`, `!cat`, `!jasmin` and
  `!java` become `Sys.chdir`, `cat`, and `shell`.
